XMSGi: РЕКОМЕНДАЦИЯ ПО РАЗВИТИЮ
Срез проекта: 29.09.2026

КОРОТКИЙ ВЫВОД

Не делайте второй самостоятельный планировщик. Оставьте XMSGi Portable стабильным приложением для личного планирования в Telegram. Развивайте Studio как главный интерфейс создания публикаций внутри оболочки XMSGi. Планировщик сохраните как общий механизм отправки, расписания и истории, а не как вторую независимую систему с собственными очередями.

На переходный период оставьте экран «Планировщик» доступным как отдельный режим. Когда Studio сможет создавать, планировать, отменять и показывать статус публикаций без потери истории, экран планировщика можно сократить до общей «Очереди и истории». Удалять работающий scheduler до этого не следует.

РОЛИ ПРОЕКТОВ

1. XMSGi Portable

Сохранить как стабильный продукт для существующего сценария: подключение личного Telegram, выбор чата, отправка, планирование, отмена и история. Не переписывать его ради Studio и не менять его поведение без отдельной причины. Это рабочая версия и страховка во время разработки нового интерфейса.

2. Оболочка XMSGi в папке XMSGi

Сделать единственным владельцем приложения: Electron, авторизация Telegram, сессия и safeStorage, IPC и его проверка, аккаунт, статус соединения, общая история и жизненный цикл планирования. Пользователь должен входить в Telegram один раз. Не заводить отдельный профиль или Telegram-клиент для Studio.

3. Studio module

Сделать главным рабочим местом контент-мейкера: подготовка текста и форматирования, вложения, шаблоны, сохранённые черновики, предпросмотр Telegram-публикации, выбор чата, отправка и планирование. Расширять функциональность постепенно; пока Telegram является единственным реально подключённым каналом, не обещать полноценную поддержку Instagram/VK/других платформ только на основании общих типов в domain.

ОСТАВЛЯТЬ ЛИ ЛИЧНЫЙ ПЛАНИРОВЩИК?

Да, оставить его логику. Не обязательно навсегда оставлять отдельный экран в нынешнем виде.

У XMSGi Portable уже есть полезные и дорогие в повторной разработке части: очередь, постоянное хранение расписаний, восстановление pending-операций, отмена в Telegram, статусы, обработка FloodWait и проверка отправки. Studio сейчас имеет собственные локальные state-списки upcoming/sent, но они не заменяют надёжную очередь host-приложения. Два независимых источника расписаний приведут к рассинхронизации и потере истории.

Рекомендуемый переход:
- Сейчас: оставить режим «Планировщик» доступным из оболочки XMSGi как резервный и привычный экран.
- В Studio: действие «Запланировать» должно передавать публикацию в общую очередь оболочки; Studio показывает результат из той же очереди.
- После проверки эквивалентности: сделать очередь/историю частью Studio или общей страницы приложения, а отдельный экран планировщика оставить только как компактный legacy-режим либо убрать.
- Не удалять useScheduler, Telegram IPC, хранилище истории и код отмены, пока новый путь не пережил реальные сценарии перезапуска, повтора, отказа сети и отмены.

ЦЕЛЕВАЯ СХЕМА

Одна оболочка и один Telegram-сеанс:

XMSGi Shell (вход, аккаунт, IPC, безопасное хранение)
    -> Studio (создание, черновик, вложения, предпросмотр)
    -> единый publishing/scheduling flow
    -> TelegramChannelAdapter / Telegram bridge
    -> одна очередь и одна история

Правило: для одной операции отправку выполняет только один слой. В embedded-режиме Studio получает scheduler callbacks от XMSGi host; не запускайте одновременно локальный обработчик Studio и host handler. Для самостоятельной разработки renderer можно оставить adapter-backed fallback, но он не должен считаться второй постоянной очередью. Со временем сведите send/schedule/cancel к одному контракту и одному набору интеграционных тестов.

ЧТО СЕЙЧАС МЕШАЕТ

1. Несовпадает draft-storage контракт. Host XMSGi использует свой старый draft-store.cjs: load возвращает объект с version/drafts/backups. Studio ожидает ответ вида success/store и данные schemaVersion/migrationVersion/savedDrafts/workspaceDraft. Host IPC сейчас возвращает load() напрямую. По коду эти контракты не совпадают, поэтому интегрированный экран черновиков может не пройти инициализацию или миграцию. Это первый блокер перед тем, как доверять Studio реальные пользовательские черновики.

Решение: выбрать один формат хранения и один владелец. Предпочтительно перенести контракт Studio schema v2 в host IPC (или добавить явный проверенный адаптер на границе), сохранив миграцию существующих пользовательских данных и резервную копию. Не просто переименовывать поля без миграционного теста. В production должен использоваться один store; не писать параллельно в две независимые копии.

2. Сейчас в host живут personal и workspace scheduler scopes. Зафиксируйте продуктовый смысл каждого: личный планировщик и публикационная очередь Studio не должны незаметно дублировать одну отправку. Если это один Telegram-аккаунт, они должны сходиться в одной истории или иметь явно показанное разделение, но не разные невидимые источники истины.

3. В Studio module собственный Electron main регистрирует только draft IPC, а не Telegram-обработчики. Реальный Telegram main/preload находится в оболочке XMSGi. Поэтому рекомендую считать Studio renderer-модулем, встраиваемым в XMSGi, а не выпускать его собственное Electron-приложение как второй продукт. Его отдельный запуск можно оставить для UI-разработки, но не считать рабочей отправкой в Telegram.

4. В host есть отдельный telegramChannelAdapter с синтетическим результатом, а в Studio module уже есть реальный adapter. Должна остаться одна реализация, которую действительно вызывает production flow. Не плодить адаптеры: сначала найдите все импорты host-заглушки, затем либо исключите её из рабочего пути, либо удалите после тестов. Канонической отправкой должен быть существующий Studio adapter или единый host service, но не два параллельных варианта.

5. Перед дальнейшими изменениями приведите Git-состояние в порядок осознанно. В проверенном дереве старый tracked путь Studio/XMSGi был помечен удалённым, а фактический Studio/Studio module — untracked. Убедитесь, что именно эта папка попадёт в репозиторий и сборку; не включайте массовые удаления или generated dist/release случайно.

ЧТО ОСТАВИТЬ И ЧТО ОТЛОЖИТЬ

Оставить:
- XMSGi Portable и его работающий Telegram scheduler как отдельный стабильный релиз.
- В оболочке XMSGi: Telegram auth/session, safeStorage, проверку IPC, Telegram core, rate-limit обработку, единую очередь/историю и восстановление операций.
- В Studio module: WorkspacePage, RichTextEditor, предпросмотр, templates, draft workflow, управляемые вложения, существующие publishingService и TelegramChannelAdapter, их тесты.
- Planner view на время перехода, пока Studio и общая очередь не доказали паритет.

Не развивать как отдельные продукты:
- Вторую Telegram-авторизацию и второй набор сессий внутри Studio.
- Локальную React-очередь Studio как самостоятельный scheduler с отдельной историей.
- Standalone Electron main/preload Studio как production runtime, если Studio будет встроена в host. Удалять эти файлы можно только после того, как сборка, тесты и UI-разработка больше от них не зависят.
- Account 2 и многоканальную публикацию до появления реальных backend adapters, отдельной авторизации и тестов. Сейчас второй аккаунт — заглушка/запасной slot, а generic domain-модель сама по себе интеграции не создаёт.

ПЛАН РАБОТ

Этап 0. Зафиксировать основу
- Убедиться, что host XMSGi и фактический Studio module сохранены в Git по правильным путям.
- Сохранить Portable как независимую стабильную версию.
- Определить, что именно собирается пользователю: host XMSGi с embedded Studio.

Этап 1. Надёжная интеграция
- Согласовать и протестировать единый draft-store schema/IPC, включая миграцию, восстановление backup и вложения.
- Проверить auth -> список реальных чатов -> отправка -> планирование -> отмена -> перезапуск -> восстановление истории.
- Проверить, что каждая операция обновляет общую очередь только после ответа Telegram, а ошибка не отображается как успех.
- Добавить integration tests на host main/preload вместе с embedded Studio; текущие adapter unit tests этого не заменяют.

Этап 2. MVP Content Studio
- Сделать Studio основной вкладкой после подключения аккаунта.
- Рабочий поток: новый пост -> текст/форматирование -> вложения -> предпросмотр -> сохранить как черновик/шаблон -> отправить или запланировать -> увидеть статус в общей очереди.
- Оставить один Telegram target и один подключённый аккаунт до надёжного end-to-end результата.
- Перенести настройки очереди и историю в Studio как режим просмотра общей очереди, а не как отдельную реализацию scheduler.

Этап 3. Только после MVP
- Добавлять календарь кампаний, несколько каналов, совместную работу, роли и дополнительные платформы.
- Для каждого нового провайдера требовать настоящий adapter, capability checks, безопасную авторизацию и тесты; не выдавать локальную domain-заготовку за поддержку платформы.

МОЯ ИТОГОВАЯ РЕКОМЕНДАЦИЯ

Идти в Content Studio. Оставить личный планировщик как надёжный общий механизм и временный отдельный экран, но не создавать второй планировщик внутри Studio. Главная оболочка XMSGi должна владеть Telegram-сеансом и очередью; Studio — содержимым и пользовательским workflow. Первый технический шаг перед расширением функций — выровнять draft-store API и проверить end-to-end сценарий через host main/preload. После этого можно постепенно сделать Studio главным экраном, не ломая Portable и не теряя уже работающий scheduler.
